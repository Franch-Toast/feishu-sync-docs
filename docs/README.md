# feishu-sync-docs 开发文档

这套文档面向**第一次接触本项目的开发者**。目标很直接：读完之后你能在自己的机器上把服务跑起来、能定位一个 bug 该改哪个文件、能理解为什么很多地方"看起来绕"其实是被飞书 API 的隐性行为逼成的设计。

所有结论均来自当前仓库代码（逐行核对），文中出现的每个 `文件:行号` 都可以直接点开验证。凡是代码里找不到依据、属于推测或需要飞书沙箱验证的内容，都会显式标注「⚠️ 待验证」。

## 三十秒版本

```
本地一个 Git 仓库（一堆 .md + 图片）  ←──双向同步──→  飞书云盘的一个文件夹
                         ↑
              常驻 Node 服务（Fastify + chokidar + WS 长连接）
                         ↑
                  浏览器工作台（React）
```

- **真相在本地**：文档正文和版本历史全部落在本地 `.git` 里，飞书只是其中一个镜像端。服务挂了、反复重启都不丢数据。
- **身份用 token**：每篇飞书文档有一个永不变的 `document_id`。这个 id 被写进本地 `.md` 文件顶部的 YAML frontmatter（称为「信封」），于是"本地文件 ↔ 远端文档"这条映射是**自描述、可精确找回**的，不再依赖文件名猜测。
- **合并用 Git 基线**：三方合并的 base 取自 `refs/heads/main` 的最新提交。每轮同步只对达到 `clean` 的条目提交新基线，所以下一轮的 base 永远是"上一次双方一致的内容"。
- **冲突绝静默覆盖**：任何自动判定不可信的情况（双方改同一段、token 被两个文件同时声明、改名目标歧义）都冻结成 conflict 状态，丢给工作台的人工裁决队列。

## 术语表

读后面几篇之前先对齐这几个词，它们在全项目里反复出现且含义固定。

| 术语 | 英文/代码标识 | 含义 |
| --- | --- | --- |
| 根目录 / root | `SyncRoot` | 一对绑定关系：一个本地目录 ↔ 一个飞书云盘文件夹。是调度和并发的最小单位 |
| 条目 / entry | `EntryBinding` | 一个本地文件 ↔ 一个远端文档（或图片）的绑定记录，键是 `relativePath` |
| 信封 | frontmatter envelope | 本地 `.md` 顶部的 `---` YAML 块，存 `feishu_token` / `feishu_root` |
| 正文 | `body` | 剥掉信封之后的内容。**所有哈希、合并、远端渲染都只作用于 body** |
| 打标 | stamp | 把 token 写进信封的动作（`writeSyncDocument`） |
| 基线 | baseline | git `refs/heads/main` 的最新提交，三方合并的 base |
| 规范化远端内容 | `canonicalRemote` | 远端 markdown 里的 `<cite doc-id>`、`<img src=token>` 还原成本地相对路径之后的内容 |
| 武装 / arm | — | 扫描阶段为某个路径写入/更新一条 `EntryBinding` 并设置其 `status` |
| 排队 / 执行 | — | 一条 pending 条目先获得 `OperationRecord(queued)`，再真正执行（`running`） |
| 回声 | echo | 自己写本地文件触发 chokidar、自己推远端触发云盘事件，导致的自激循环 |
| 车道 | lane | `task_queue.ts` 里每个 root 对应的一条 Promise 链，保证同 root 串行 |

## 项目当前位置

- 五包 monorepo（core / storage / feishu / server / web），TypeScript 严格模式，Node ≥ 20。
- 测试：node:test 211 个（core 61 + storage 11 + feishu 16 + server 123）+ web 端 vitest 79 个，共 **290** 个用例，全绿。
- 远端只支持**飞书云盘文件夹**；知识库（wiki）在 `listTree` 里直接抛错，见 [07 · 已知缺陷](07-known-issues.md)。
- 通知（系统通知 / 飞书机器人）接口已预留但**未开放**，当前实现是 `NoopNotifier`。
